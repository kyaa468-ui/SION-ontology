# 수정계획 4 구현과 실행 계약

이 문서는 새 코드의 실행 계약을 설명한다. 실제 AI 반복 실험이나 운영 개선 확인의 완료 증명은 아니다. 원래 수정계획과 사용자가 작성한 문제 분석 문서는 보존한다.

## 실행

저장소 루트의 가상환경에서 다음 명령을 사용한다.

```sh
.venv/bin/python agent/run.py improvement-status
.venv/bin/python agent/run.py improve --no-ai
.venv/bin/python agent/run.py improve --with-ai
.venv/bin/python agent/run.py migrate-opportunities
.venv/bin/python agent/run.py migrate-independent-cases --as-of YYYY-MM-DD --knowledge-as-of ISO_TIMESTAMP
.venv/bin/python agent/run.py migrate-scoring-targets --dry
.venv/bin/python agent/run.py migrate-research-usage
.venv/bin/python agent/run.py migrate-holdout-scopes
.venv/bin/python agent/run.py build-trace-view --view-limit 50
.venv/bin/python agent/run.py rebuild-storage-index --dry
.venv/bin/python agent/run.py retention-report
.venv/bin/python agent/run.py retention-collect --dry
```

`improve --with-ai`는 `agent/config/ontology/improvement.json`의 연구 모델과 저장 예산, 일일 비용 여유가 확인될 때만 공급자 호출을 시작한다. 장마감 평가 뒤에도 같은 작업자가 실행된다. 이 코드 변경 작업에서는 실제 유료 호출·주문·정책 적용·운영 원본 삭제를 실행하지 않았다. 대시보드는 기존 검토 서버의 `/improvement`에서 제공한다.

## 기록과 책임

- `opportunity_cases`: 회차·종목·방향마다 기회 하나. 미제출·거절·관망·차단도 포함하고 전제 수로 분모를 늘리지 않는다.
- `assessment_contracts`: 등록된 측정 정의와 유한한 표현식으로 MA20 외 전제를 평가한다. 전부/하나 이상/집계, 결측, 당시 알 수 있었던 revision, 정정 대기를 구별한다. 인과 주장은 자동 입증하지 않는다.
- `investigation`: 먼저 범위를 고정하고 노출을 예약한 뒤 조회·검사를 반환한다. 진단은 실제 검사·참조 및 경쟁 설명을 요구한다.
- `change_registry`: 수정 목표·유지 대안·다른 대안·선택 이유·실제 패치·검증·관찰·복구를 기준 버전에 묶는다.
- `semantic_experiments`: 운영 제출 검사기를 사용하는 interpretation → bull → bear → lead의 두 실험군. 가짜 provider·저장 응답 재생·실제 새 호출은 별개 결과다.
- `change_application`: 정책 채택과 직접 튜닝 경로의 최종 적용 창구. 기존 정책 intent/commit과 새 적용·관찰 기록을 연결한다.
- `change_observation`: 적용, 실제 소비, 기대 동작, 재발, 부작용, 관찰 종료를 구별한다.
- `research_budget`: KST 날짜의 확정 비용과 미정산 예약액을 합산하는 하루 5달러 원장. 모호한 타임아웃은 환불이 아니다.
- `research_usage_ledger`: 원본 dataset과 분리한 사용 이력. 명시적 이행 검증 후 reader를 전환하며 새 application ID도 같은 원천이면 기존 사용 이력을 이어받는다.
- `research_capacity`: 선택적 연구의 바이트·사례 상한과 영속 예약. 필수 거래 기록을 버리는 파일시스템 할당량은 아니다.
- `workspace_reclamation`: 종료된 코드 시험 사본의 소유 확인·격리·물리 회수와 중단 재개.
- `retention_inventory`: 수정계획 R01–R34의 소유 모듈·소비자·종료 계약. 운영 ontology root만 대상으로 하며 리허설 사본을 자동 편입하지 않는다.

새 상태는 저장소 루트 기준 `agent/work/ontology/improvement/state.sqlite3`에 저장한다. 본문 SHA, immutable revision, 필수 내용 연결, 노출 원장, 호출 예약을 보관한다. 상태 조회와 GC 보고는 저장소를 자동 생성하거나 손상을 복구하지 않는다. 현재 거래의 위험·주문·체결 원장은 이 DB와 분리되어 있다.

## 미설정 값의 처리

초기 `auto_apply`는 비어 있다. 기존 tuning 허용 목록을 새 자동 적용 권한으로 승격하지 않는다. `validation_criteria`, `observation_criteria`, 평가 기간 상한, 저장 예산, 알림 채널도 운영자가 정해야 하는 항목은 빈 값으로 둔다. 해당 값이 필요한 단계는 구체적인 대기 사유를 반환한다. 조사 준비와 기능 시험은 별도로 가능하다.

권한에는 실행 주체, 대상, 변경 종류, 동일한 scope, 만료, 일일 횟수, cooldown, 누적 한도가 필요하다. 변경의 검증 기준 hash와 관찰 기준은 서버 설정과 일치해야 한다. 검증 미달은 수동 승인으로 우회하지 않는다.

`change_limits`에는 숫자 변경의 회당·누적 절대 변화 한도, 값의 상하한 또는 패치 바이트·누적 바이트·변경 줄 수 한도가 필요하다. 횟수·변경량은 실행 주체와 수정 대상별로 누적하며 되돌림으로 초기화하지 않는다. 같은 적용 요청의 재개는 새 적용으로 중복 계산하지 않는다.

실제 단계 비교는 공급자가 보고한 `modelUsage`의 모델 ID가 등록된 `model_version`과 일치해야 한다. 모델을 확인할 수 없어도 이미 발생한 비용은 정산한다. `research_model_version`도 별도 재평가에 필요하다. 가짜 provider로 실행한 동일 실험 ID를 실제 호출 결과로 승격할 수 없다.

기간이 있는 새 전제는 관측 개수와 실제 거래소 달력의 기간을 함께 검사한다. 지원 기간 상한이나 당시 사용 가능한 달력이 없으면 `capacity_blocked`로 남긴다. 미지원 평가기는 확장 요청을 남기며 평가 성공으로 처리하지 않는다.

코드 패치는 별도의 격리 시험과 배포 어댑터가 필요하다. 실행 중인 Python 프로세스에 파일을 바꿨다는 이유만으로 새 코드 사용을 주장하지 않는다. `offline_single_file` 배포는 호스트가 남긴 유한한 중지 확인 lease와 원본 hash를 요구하며 다음 프로세스부터 유효하다. 지원하지 않는 배포 환경에서는 패치와 검사 결과를 보존하고 적용을 대기한다.

## 보관의 범위

완료 사례는 최초 종료일 기준 20거래일, 상세 재실험은 원래 판단일 기준 20거래일이다. 확인된 거래소 달력 없이 평일을 세어 삭제하지 않는다. 정정 대기는 5거래일, 실질 진척 없는 연구의 만료는 30일이다.

새 SQLite 기록 정리는 활성 작업·현재 적용·유효한 pin에서 필수 내용 연결을 따라가며 공유 내용과 순환 연결을 처리한다. 필수 내용의 누락·손상은 삭제를 차단한다. 회수는 논리 만료 commit 후 SQLite 물리 공간 회수로 나뉜다.

기존 v1/v2 원본은 소비자별 동등성 증명과 전환이 확인되기 전까지 보호한다. `independent_cases.migrate()`는 지원 필드의 동등성을 검사하고 새 사례 reader를 켜지만, 다른 소비자의 원본 삭제까지 허가하지 않는다. 이 제한은 미완료된 전환을 안전한 삭제로 가장하지 않기 위한 것이다. 실제 운영 저장량 절감은 별도 측정 없이는 주장할 수 없다.

`migrate-opportunities`는 기회와 조사 증거를 수집하는 명령이며 `independent_cases.migrate(market_as_of, knowledge_as_of)`와 다른 작업이다. 전자는 응답의 `next_cursor`를 다음 실행의 `--revision`으로 전달한다. 후자는 MA20 사례 비교의 고정 시점 동등성을 확인한 뒤 해당 reader만 전환한다. 이번 작업에서 운영 이력을 일괄 이관하거나 삭제하지 않았다.

큰 공통 입력은 조사 사례에 다시 펼치지 않는다. 실제 전달 텍스트·대상 측정값·단계 출력·실행 결과를 저장하고, 전체 재현에 원본이 필요한 항목에는 `original_required`를 남긴다. 이 표시가 있는 원본은 독립 증거로 대체됐다고 간주하지 않는다.

새 실제 AI 재실험은 원래 판단일 기준 상세 지원 범위를 검사한다. 범위를 넘은 경우 사전 등록된 유효한 검증 pin이 필요하다. 기존 검증의 등록·입력 수집·시장자료 import도 같은 Q3 범위를 검사한다. 검증 구간은 사전 등록·유한 만료·설정된 저장 예약을 요구하며, 확정된 최종 결과는 구간 예약을 종료한다. 범위 등록 이후 새로 생성된 사례도 기간·종목이 일치하면 보호하며, 그 사례의 필수 근거까지 함께 보존한다. 새 화면 생성은 독립 사례의 범위를 먼저 고르고, 이행을 검증한 holdout 조회는 활성 예약 요약을 읽는다. 완료 화면과 그 사용 기록의 v1/v2 물리 회수는 아래 계약을 따른다. 다른 원본 유형의 소비자 전환은 별도로 필요하다. 선택적 연구의 입장 제어는 실제 WORK 디렉터리의 파일 크기를 별도 감사하며, 필수 기록까지 포함한 엄격한 전체 디스크 상한은 보장하지 않는다.

## 관계 정정과 재평가

`semantic_dependencies.changed(event)`는 실제 읽은 ID와 조회 조건을 함께 비교한다. 기존 read 목록에 없던 새 관계도 영향 후보가 될 수 있다. 원래 chain을 무효화하고 재평가 큐를 만든다. `supply_inputs`는 호스트 어댑터가 확정된 정정 chain·receipt·지침을 제공하는 경로이며 조사 AI 도구에 노출하지 않는다.

작업자는 정정 입력이 없으면 `inputs_pending`, 고정 모델이 없으면 `configuration_pending`으로 둔다. 입력이 갖춰지면 네 역할을 다시 실행한다. 원래 판단 기록을 덮어쓰거나 과거 주문을 다시 보내지 않으며, 현재 사용 자격은 새 운영 판단이 만들어질 때까지 무효 상태다. 모든 외부 데이터·매핑 변경을 자동으로 정정 입력으로 변환하는 어댑터가 구현된 것은 아니다.

## 기존 경로 변경

정기 `case_review`의 모델 학습·발행·fold·예측 평가와 판단 접수의 신규 예측 callback은 중단한다. 모델 없이도 복기 결과 자체의 완료 commit을 만들고 제안이 읽을 수 있다. 과거 모델 기록 reader는 호환성을 유지한다.

`tuning.apply`는 설정·교훈을 직접 쓰지 않고 조사 대기 요청을 만든다. 기존 정책 채택 CLI도 진단에 연결된 변경, 독립 검증, 등록 권한을 통과해야 한다. 매매 판단의 기존 손절·위험·수량 규칙은 이 전환의 수정 대상이 아니다.

## 검증 결과의 해석

기능 시험 통과, 격리 소스 시험, 실제 새 AI의 반복 비교, 운영에서의 버전 소비, 관찰 종료 판정은 각각 별도 증거다. 최종 보고서는 실행한 시험과 실행하지 않은 단계를 구별한다. 공급자 호출 없이 측정한 응답 바이트나 실행 시간을 실제 토큰·달러 절감으로 환산하지 않는다.


## 추가 저장·복구 계약

`storage_bytes`, `case_count`, `research_job_bytes`가 비어 있으면 새 실제 연구 호출, 상세 검증 구간 예약, 코드 시험 사본 생성을 차단한다. 각 입장 검사는 현재 `WORK`의 실제 파일 크기와 미완료 예약을 보수적으로 합산한다. 사본 예상 크기가 작업 예산을 넘으면 내용을 자르지 않고 거절한다. 완료 확인 전 예약은 재시작이나 자정만으로 풀지 않는다. 필수 주문·체결·기회 기록은 계속 보존하며, 그 기록 때문에 상한을 넘으면 다음 선택적 연구가 대기한다. 이 검사는 별도 파일 metadata 감사 비용을 가지며 전체 이력이 늘어도 상수 비용인 것으로 보고하지 않는다.

`migrate-research-usage`는 원본 사용 기록과 dataset을 최초 한 번 순회하여 사용 원장의 동등성을 검사한다. 성공한 경우에만 사용 여부 reader를 원장으로 전환한다. 이후 사용 callback은 새 원장에 즉시 반영한다. 원본을 가리거나 같은 원천에 새 application ID를 부여한 시험에서도 사용 상태가 유지된다. holdout 판정은 원본 전제 목록뿐 아니라 이 별도 원장의 종목·발생 시각 범위도 확인하므로, 원본 전제와 dataset이 사라져도 이미 노출된 자료를 독립 자료로 승격하지 않는다. 알려지지 않은 사용 schema는 전환을 막고, 원장에 행이 없다는 이유로 독립 자료라고 판정하지 않는다.

관측 전달은 종목·필요 관측일을 먼저 선택한다. 한 번에 200개를 넘으면 전달의 필요한 측정값과 cursor를 영속 대기열에 남기고 작업자가 나머지를 처리한다. 같은 전달을 재처리해 관측 수를 늘리지 않는다.

코드 사본은 소유 manifest를 먼저 기록한 뒤 임시 디렉터리에서 준비하고 원자적으로 공개한다. symlink·환경 설정 비밀 파일은 복사 대상에서 제외한다. 공개 직후 중단돼도 파일 hash를 검증하여 재개한다. 종료된 사본은 사용 잠금을 확인한 뒤 격리 이름으로 옮겨 삭제하며, 중간 삭제 실패도 같은 작업 ID로 재개한다.

`retention-collect`는 `--dry`를 생략했을 때 새 improvement 저장소, 소유가 확인된 시험 사본, 종료가 증명된 주문·정산 호출 행, 지원이 끝난 조회 화면의 manifest/commit/blob/index 항목을 정리한다. 다른 기존 원본은 소비자 전환이 확인되기 전까지 보호한다. 이번 변경 작업에서는 운영 이관·회수 명령을 실행하지 않았다.


## 구형 프롬프트 실험과 직전 복기 비교의 전환

구형 `prompt_pair` 경로도 실제 호출 전 등록된 `prompt.model_version`을 요구하고 그 정확한 버전을 요청한다. 공급자가 보고한 모델 ID가 다르거나 확인되지 않으면 비용은 정산하되 검증 성공으로 받지 않는다. 실험 ID는 검증 명세·원본 입력·실제/가짜 실행 구분으로 고정하며, 재개 시 완료된 trial과 단계 응답을 그대로 사용한다. 전송 후 응답이 남지 않은 호출은 자동 재전송하지 않는다. 예산·용량 입장 대기는 최종 결과로 확정하지 않고 같은 요청으로 다음 실행에서 재개하며 반복 수·분모를 줄이지 않는다.

새 복기는 `review_comparison`에 변화 판정에 필요한 필드의 서명을 별도 commit으로 저장한다. 다음 복기의 신규/변경/동일 비교는 이 요약을 사용한다. 기존 복기는 `python agent/run.py migrate-review-comparison --review-id <완료 복기 ID>`로 해당 소비자의 동등성만 검증해 전환할 수 있다. 원본 dataset이 없고 요약도 없으면 모든 사례를 새 사례로 바꾸지 않고 비교 자료 부재를 보고한다. 사례 화면·검증 등 다른 소비자의 원본 삭제 권한은 이 전환으로 생기지 않는다.

연구 사용 원장 이행을 검증한 저장소에서는 holdout 노출 검사도 원본 전제 전체를 다시 읽지 않는다. 사용 자료의 원래 종목·시각을 확정할 수 없는 원장이 있으면 독립성은 확인 불가로 처리한다. 개별 자료의 조회 보호는 해당 전제 또는 보존된 원천 식별을 직접 확인하며, 보호 구간이 있는 상태에서 출처를 찾지 못한 자료를 노출하지 않는다. 시험 사본 회수는 실패한 첫 항목을 다음 번으로 넘기는 cursor를 사용해 뒤의 작업이 계속 처리되도록 한다.


## 주문·비용·연구 노출 기록의 종료

새 주문 ID는 호스트가 `order-g<세대>-<무작위값>`으로 발급한다. 호출자가 제공한 ID는 이미 예약된 것만 사용한다. 삭제한 ID나 임의 ID로 새 예약을 만들 수 없다. 기존 Hook의 결정적 ID는 원래 회차와 연결된 발급 기록으로 전환한다. 상세 지원 기간 밖의 미전송 요청은 다시 전송할 수 없다.

거절·모의 완료 또는 브로커에서 전량 체결이 확정된 요청만 종료 후보가 된다. 브로커 완료 기록의 hash·요청 수량·원래 payload를 검증한다. 전량 체결 요청도 종료 이후의 완전한 계좌 관측이 있고 현재 보유가 없을 때만 회수한다. 부분 체결·응답 유실·충돌·불완전 계좌·진행 검증 구간은 보존한다. 주문 SQLite의 삭제 행은 재사용 공간이며, 별도의 물리 파일 축소를 했다고 보고하지 않는다.

연구 비용 원장은 지원 기간 밖의 `settled/cancelled` 행만 고정 크기 식별 체크포인트와 누계로 옮긴다. 진행 소유 작업, 예약 중인 호출, 미정산·초과 비용은 남긴다. 오래된 날짜의 비용 조회는 `history_scope=expired`, `actual_usd=null`로 반환하며 0달러로 꾸미지 않는다. 두 식별 bitset은 합계 2MiB이고 retired call/provider ID를 다시 실행하거나 중복 정산하지 못하게 한다.

전송 직전에도 현재 한국 날짜의 비용과 다른 미정산 호출을 다시 확인한다. 자정 전에 예약하고 다음 날 보내는 호출은 실제 전송일 예산으로 옮기며 원래 예약 시각과 전송 시각을 각각 남긴다. 전송 전 중단된 호출만 같은 ID·내용·최대 비용으로 재개한다. 용량과 비용의 전송 권한은 한 트랜잭션에서 확정하므로 경쟁 요청은 한 번만 전송할 수 있고 패한 작업자가 전송 중인 작업의 용량을 해제하지 않는다. 설정·용량·예산 대기는 같은 실험 분모를 유지해 재개하며, 응답이 유실된 전송은 자동 재호출하지 않는다.

기회 사례가 회수될 때 연구 노출의 원천 ID도 별도 1MiB 체크포인트에 반영한 뒤 개별 행을 제거한다. 현재 소비자는 원천별 노출 여부만 사용하므로 동일 원천의 중복 owner 행은 한 행으로 합친다. 이 체크포인트들과 비용 체크포인트는 거짓 음성을 허용하지 않는 보수적인 식별 필터다. 충돌 가능성이 있는 새 ID도 차단될 수 있으며 이를 확정된 중복과 구분한다. 차단을 피해 다른 ID로 자동 재시도하지 않는다. 손상된 체크포인트는 미사용·미호출로 해석하지 않는다. 활성 주문과 미정산 비용 등 필수 안전 상태 전체에 영구적인 디스크 상한이 생긴 것은 아니다.

## 조회 범위와 검증 예약의 전환

`migrate-holdout-scopes`는 원본 예약·해제 기록과 새 활성 예약 집합을 대조한다. 성공한 경우에만 `validation_holdout.reservations`의 전체 이력 조회를 전환한다. 새 발행 전 동기화 intent를 남기고 원본 commit 확인 후 요약을 확정한다. 그 사이 중단됐거나 활성 집합의 행·hash가 달라지면 조회를 차단한다. 원본 해제·등록의 의미를 바꾸거나 독립성 증명을 대신하지 않는다.

`build-trace-view`의 기본 경로는 `scoped_trace`다. 검증된 달력과 holdout 조회 이행이 필요하며, `--case-ids`로 명시한 사례 또는 지원 기간 내 사례를 발생 시각·ID 순으로 최대 50개 선택한다. `--view-limit`은 1~200이다. 본문 크기를 확인한 뒤 선택된 revision과 필요한 근거만 읽으며 기본 원문·화면 크기 한도는 4MiB다. 잘린 범위와 큰 세부 내용은 `partial/detail_limit/capacity_blocked`로 표시한다. 원본을 다시 읽어 없던 과거 사실을 재구성하지 않는다. 공통 자료의 holdout 노출 범위가 예전 사례에 확정돼 있지 않으면 해당 근거는 보호한다.

기존 스냅샷과 구형 Python 조회 API의 읽기 호환은 남아 있다. 기본 CLI에서 전체 과거 파일 수집·원본 기반 화면 재구성을 호출하지 않는다. 연구 노출은 화면 commit 전에 기록하며 조회 준비 실패가 이미 기록된 노출을 취소하지 않는다.

선택적 화면 생성도 설정된 저장 예산을 먼저 예약한다. 한도를 초과한 화면은 사용 이력을 만들기 전에 차단한다. 판단 이유와 행동은 선택된 사례에 이미 확정된 근거에서 기존 화면의 표시 필드로 전달하며, 세부 원문을 읽지 못한 판단은 요약만 있다는 상태를 남긴다.

## v1/v2 파일과 공유 blob의 회수

처음 연결한 원본 유형은 지원 기간 밖의 완료 조회 화면이다. manifest·projection·commit 동등성을 확인하고, 실행 중인 화면 서버의 세션 잠금이 없을 때 회수 후보로 삼는다. `migrate-research-usage`의 동등성 검증이 끝났고 해당 화면 소유의 사용 기록까지 원장과 일치하면 그 원본도 함께 정리한다. 다른 원본 기록은 계속 live root로 취급한다.

회수된 사용 기록이 소유한 빈 잠금 DB도 소유 ID·내용·진행 sidecar가 없음을 확인한 경우에만 회수한다. 알 수 없는 테이블이나 진행 흔적이 있는 잠금은 보존한다. 이 처리가 없으면 화면 원문을 지워도 사용 기록마다 작은 잠금 파일이 계속 쌓인다.

모든 남은 v1/v2 기록을 해당 codec으로 검사해 실제 blob 연결을 확인한다. 사용자가 작성한 JSON의 ID 문자열을 참조로 추정하지 않는다. 다른 살아 있는 기록이 공유하는 blob은 남기고, 손상·알 수 없는 저장 버전·symlink·불완전 commit으로 연결을 증명하지 못하면 해당 회수를 중단한다. 한 배치는 최대 200개 blob과 제한된 수의 화면을 처리한다. 최초 원본 목록 확인은 최대 100,000개 파일의 명시적 감사이며 상수 시간이라고 주장하지 않는다.

읽는 동안 lazy 객체의 resolver가 저장 디렉터리 잠금을 유지한다. 발행은 동일한 보호와 영속 세대 번호를 사용한다. 회수는 표시 작업 동안 전체 쓰기를 막지 않고, 마지막 짧은 정리 단계에 대기 없는 배타 잠금을 시도한다. 읽기·쓰기 중이거나 표시 이후 세대가 바뀌면 다음 실행으로 미룬다. TTL만으로 살아 있는 프로세스를 종료하지 않는다. POSIX 디렉터리 잠금을 지원하지 않는 환경에서는 기존 읽기·쓰기를 유지하고 실제 회수는 지원하지 않는다.

파일 삭제도 저장 세대의 변경이다. 회수 전 준비한 다른 정리 계획이나 인덱스는 삭제 뒤 설치할 수 없다. 논리 만료 직후 중단되어 세대 번호를 아직 올리지 못했어도 미완료 회수 기록이 인덱스 교체를 차단한다. 이 조정은 새 프로토콜을 사용하는 프로세스 사이에서 검증했다. 운영 회수 전에는 이전 코드의 실행 프로세스가 모두 종료되고 새 코드로 전환됐는지 별도로 확인해야 한다.

삭제 목록과 논리 만료를 먼저 확정한 뒤 manifest·commit·blob·index를 정리한다. 중단된 목록이 있으면 같은 목록으로 복구하며, 복구 전 새 발행을 차단해 회수 예정 blob을 새 기록에 붙이지 못하게 한다. 논리 만료된 화면은 `expired`로 반환한다. 새 화면 ID는 원래 생성일을 포함하며, 닫힌 구형 ID 이름 공간도 재발급하지 않는다. 물리 회수 후 원문을 복원할 수 있다고 약속하지 않는다.

새 검색 인덱스는 작은 단위로 빈 SQLite 페이지를 반환한다. 구형 인덱스는 `rebuild-storage-index`로 원본에서 새 사본을 만들고 세대가 같을 때만 원자적으로 교체한다. 인덱스가 없거나 오래돼도 원본 manifest가 권위 있는 자료다. 보고서의 실제 파일 바이트에는 체크포인트·인덱스·임시 공간을 포함하며, 공유 때문에 회수하지 못한 바이트를 따로 기록한다.

일반 판단·정책 증명·평가·검증 입력 등 모든 R유형의 원본 소비자가 전환된 것은 아니다. 이 원본들의 필수 소비와 현재 보유·미정산 주문은 삭제 허가가 생길 때까지 보존한다. journal은 아래의 별도 전환 계약을 따른다. 이번 작업은 격리 시험으로 확인했으며 운영 원본을 이관하거나 삭제하지 않았다.

## 거래 로그의 체크포인트와 상세 보관

`journal-retention-report`와 `migrate-journal --dry`는 읽기 전용으로 후보와 보존 경계를 계산한다. `migrate-journal`은 명시적인 최초 전환이며, 성공한 뒤에만 일반 `retention-collect`가 journal 정리를 포함한다. 기본 경계는 확인된 달력의 20거래일이다. 진행 검증·holdout의 유한 예약이 더 오래된 원문을 필요로 하면 그 시작일까지 journal 전체를 보존한다. 확인된 달력이 없으면 새 만료 범위를 정하지 않는다.

체크포인트는 전체 체결 횟수와 경쟁 시작일 이후 집계를 분리한다. 열린 포지션의 수량·원가·진입 정보, 기존 가격 기준 청산 수익률 누계, 판단·차단 횟수, 마지막 회고, 튜닝 횟수·키별 마지막 변경 차수를 보존한다. 현재 시장 보정값이 바뀌어도 관망 확신도 분포를 다시 계산할 수 있도록 원래 확신도와 당시 국면을 유지한다. 가격 기준 수익률 누계를 수수료 반영 순손익으로 표시하지 않는다.

현재 잔고와 부분 체결을 대조하는 logger에는 이전 구간의 순수량과 미완료 체결 보정 원본을 전달한다. 최근 체결 ID도 전체 체결 순서를 이어간다. `fill_fixes` 정의를 사후에 바꾸면 이미 정리된 원문을 새 정의로 재계산했다고 꾸미지 않고 보정 자료 불일치로 중단한다. 공개 상태에는 거래 상세 보관 종료 날짜를 표시한다. 별도 Sigma 저장소와 실행 중인 과거 버전 프로세스까지 전환됐다는 의미는 아니다.

새 튜닝 입력은 설정된 행·바이트 상한 안에서 최근 상세, 전체 경쟁 집계, 확신도 분포를 제공한다. 현재 보유 정보가 한도를 넘거나 결과 채점에 필요한 고유 사례가 한도를 넘으면 `capacity_blocked`를 반환한다. 제한된 상세 배열을 전체 이력으로 표시하거나 잘린 사례만으로 성공률을 계산하지 않는다. 과거의 경쟁 시작일로 바꿔 사라진 구간을 요구하면 `JOURNAL_COMPETITION_SCOPE_EXPIRED`로 중단한다.

전환은 원본 읽기 잠금 아래에서 새 파일을 준비하고, 전체·경쟁 범위의 소비자 집계 hash가 같은지 확인한 뒤 원자적으로 교체한다. 평상시 교체 잠금 안에서는 전체 파일을 다시 읽지 않는다. 준비 중 새 기록이 추가됐거나 다른 reader가 살아 있으면 다음 실행으로 미룬다. 검증 예약의 쓰기 트랜잭션 아래에서 보존 경계를 다시 확인하고 교체가 끝날 때까지 예약 발행을 직렬화한다. 새로 추가된 보호 범위나 미완료 holdout 발행이 있으면 정리를 미룬다. 필수 기록 writer는 짧은 교체가 끝나기를 기다린다. 교체 계획·체크포인트 세대·현재 파일은 별도 제어 DB로 결합하며 누락·불일치를 새로운 빈 로그로 재생성하지 않는다.

중단된 교체는 새 달력이 없어도 이미 확정된 계획과 파일 hash로 복구한다. 준비만 하다가 프로세스가 종료되면 소유한 임시 파일의 잠금이 해제됐는지 확인하고 그 파일만 정리한다. 고정 크기 요청 식별 필터는 오래된 run ID 재사용을 차단하며, 충돌 가능성도 확정 중복과 구별해 차단한다. 다른 ID로 자동 재시도하지 않는다. 재현 입력에는 체크포인트 세대·hash·퇴역 이력 hash와 실제 캡처한 파일 범위의 hash를 함께 기록한다.

체크포인트 본문은 최대 2MiB, 요청 식별 필터는 32KiB다. 열린 보유·미완료 체결 보정 등 필수 상태 때문에 한도를 넘으면 원문을 삭제하지 않고 전환을 중단한다. 이 계약이 필수 안전 상태나 전체 저장소에 엄격한 영구 상한을 부여하지는 않는다. 100/1,000/5,000쌍의 종료 거래와 최근 체결 1개로 만든 격리 시험에서 거래 로그 제어 DB와 검증 예약 DB까지 포함한 정리 후 파일 크기는 163,023/163,029/163,033바이트였으며, 운영 디스크·토큰·비용 절감을 측정한 값은 아니다.

## 자료 사용 이력의 유한 압축

`migrate-research-usage`의 동등성 검증을 마친 저장소에서만 `retention-report`와 `retention-collect`가 사용 이력 압축을 포함한다. 기본 지원 하한은 확인된 달력의 20거래일이며, 진행 검증·holdout 예약이 있으면 그 시작일까지 보존한다. 진행 중인 사용 주체, 최근 사용, 필수 상태 참조, 출처 시각을 확인할 수 없는 행은 보호한다. 미완료 holdout 발행이나 사용 원장 오류가 있으면 압축을 중단한다. 후보 선정과 예약 확인·압축·행 삭제는 같은 쓰기 트랜잭션 안에서 수행한다.

기간 밖 `usage_alias`와 더 이상 필요한 alias가 없는 `research_exposure`는 1MiB 고정 식별 필터와 하나의 지원 하한·누계 hash로 옮긴다. 같은 원천을 다른 자료 ID로 다시 넣어도 과거 사용 가능성이 이어지며, 이미 압축한 ID의 조회는 전제 원문을 읽지 않는다. 만료 원천의 반복 import도 개별 행을 다시 쌓지 않는다. 필터 충돌은 `prior_exposure_or_checkpoint_collision`로 구별하며 독립 자료 자격을 주지 않는다. 충돌한 ID를 바꿔 자동 재시도하지 않는다. 원문과 압축 기록 어디에도 양성 사용 증거가 없으면 `unknown`이며 미사용 증명이 아니다.

원천별 상세를 이미 압축한 과거 기간의 집합 조회는 `usage_detail_scope_expired`를 반환한다. 빈 노출 목록을 근거로 그 기간의 검증을 독립적이라고 판정할 수 없다. 한국 시간 보관 경계의 새벽 기록도 UTC 날짜 비교로 잘못 만료되지 않게 검사한다. 체크포인트 본문과 별도 identity marker가 없거나 손상되면 조회를 차단한다.

이 압축은 사용 상태 소비자의 전환이며, 원래 dataset·화면·검증 결과를 일괄 삭제하는 권한은 아니다. 새 checkpoint의 고정 비용 때문에 작은 저장소에서는 파일 크기가 증가할 수 있다. 원천 시각 미확인 행과 실제 진행 작업 등 필수 상태 전체에 영구적인 디스크 상한을 부여하지 않는다.

## 정책 검증 증명의 전환

`migrate-policy-proof --dry`는 현재 정책 포인터의 전환 가능성과 증명 크기를 읽기 전용으로 확인한다. `migrate-policy-proof`는 원래 adoption·검증 결과·결과 commit·등록 명세를 검증한 후 `POLICY_PROOF@v1`과 활성화 ID에 결합한 증명 참조를 발행한다. 현재 숫자 설정이나 정책 포인터는 변경하지 않는다. 만료되거나 기준 소스가 달라진 정책을 다시 활성화하는 명령도 아니다.

증명에는 등록 기준·실제 기준 검사·독립성·완전성·채택 자격, candidate params, 정책/명세/결과/활성화의 hash, 검증 결과 commit을 보존한다. 성공 flag 하나를 복사해 기존 검사를 생략하지 않는다. 새 reader도 후보 수치와 정책 내용·범위, 이전 revision, 활성화 intent, 현재 소스·설정 버전과 유효 기간을 확인한다. 전환 전후 `policy_registry.snapshot` 결과가 같아야 한다. 증명은 최대 2MiB이며 초과하면 원래 증명 사슬을 보존한다.

증명만 발행하고 참조 발행 전에 중단되면 기존 reader를 유지한다. 재시도는 같은 증명 ID를 사용한다. 증명 참조가 있는 상태에서 증명이 누락·변조됐으면 원래 사슬로 조용히 돌아가 성공 처리하지 않고 `recording_error`를 반환한다. 전환 후 정책 확인과 교훈 제공은 원래 검증 결과·adoption reader 없이 가능하다. 재실험·상세 화면 등 다른 소비자의 원본 필요 여부는 별도 판단하므로 이 명령만으로 과거 검증 파일을 삭제하지 않는다. 활성 package·activation intent·되돌리기에 필요한 이전 수치는 계속 보호한다.

## 판단 조건 입력의 확정과 보관

새 판단을 접수할 때 정책 조건과 고정 검증 입력에서 실제 사용하는 12개 필드를 별도로 확정한다. features·signed flows·stratum·adoption, 근거 목록·비교 문맥, 적격 여부와 이유, 당시 선택 관측·정의·설정·시장 국면을 보존한다. 전제가 없는 판단도 지원하고 여러 전제 중 첫 전제 하나로 채택 논거의 의미를 대체하지 않는다. 판단 hash와 값 hash를 확인하므로 다른 판단이나 변조된 값으로 재사용할 수 없다.

이 입력은 개선 저장소에 보관하며 관련 판단 기회에 필수 내용으로 연결한다. 최근 지원 범위, 진행 중인 부모 사례와 등록 검증 범위가 보호하고, 소비가 끝나면 기존 회수 절차가 본문과 revision을 함께 정리한다. 별도 무기한 원본 저장소를 추가하지 않는다. 종료된 입력을 요청하면 `POLICY_INPUT_DETAIL_EXPIRED`를 반환하며 원본을 자동 재구성하지 않는다. 아직 전환되지 않은 구형 판단은 지원 범위 안에서 기존의 실제 보관 원문을 이용한다. 입력 확정에 실패하거나 크기 한도를 넘은 경우 원본 삭제 권한이 생기지 않는다.

## 정기 예측모델 원본의 사용 종료

`migrate-model-retention --dry`는 구형 모델·발행·예측·예측 시작 기록을 읽기 전용으로 검사한다. `migrate-model-retention`은 이 구형 저장 영역의 생산을 종료하고, 최초 자료 수와 ID·내용 hash 집합을 확정한다. 이행 명령만으로 원본을 삭제하지 않는다. 정기 모델 생성 중단은 기존 변경 그대로이며, 이행 후에는 직접 재요청한 과거 예측 callback도 새 모델·예측 파일을 만들지 않는다. 별도 질문을 위한 새 모델 연구를 이 폐쇄된 저장 영역에 임의로 추가할 수 없다.

이행은 일반 보관 정리를 시작하기 전에 수행한다. 기존 모델 조회 중에는 저장소 잠금 때문에 이행이나 회수를 미룬다. 이행 경쟁에서 이미 진행된 회수 하한·종료 상태를 초기 상태로 덮어쓰지 않는다. 최초 전환의 감사 한도는 20,000개 기록과 8MiB의 식별 메타데이터이며, 한도를 넘거나 기록 형식·ID·내용을 확인하지 못하면 조용히 일부만 전환하지 않고 중단한다.

이행 후 `retention-report`와 `retention-collect`에 모델 영역의 후보가 포함된다. 예측은 시작 기록과 ID·대상·발생 시각이 일치하고, 연결된 전제 사례의 종료가 확인되며, 종료일·발생일·기록일·시작일이 보관 범위 밖일 때만 시작 기록과 함께 회수한다. 진행 사례, 완료 미확인, 필수 참조, 최근 기록은 보존한다. 모델은 발행 commit이 확인되고 발행·사용 가능 시각과 적용 기간 종료가 모두 보관 범위 밖이며, 남아 있는 예측이 참조하지 않을 때 회수한다. 미완료 예측 시작 기록이 있으면 필요한 모델을 임의로 추정해 삭제하지 않는다.

진행 검증·holdout 예약은 그 시작일까지 보존 범위를 넓힌다. 회수 계획을 만든 뒤 새로운 보호 범위가 등록되거나 사례 상태가 바뀌면 삭제 전에 중단한다. 필수 사례가 먼저 정리될 때는 예측 원본 hash와 확정 종료 출처를 작은 소유 증명으로 넘긴다. 예측 원본을 회수한 뒤 이 증명의 본문·revision도 정리한다. 전환 전에 이미 사라진 종료 증명은 만들어내지 않으며, 해당 예측은 `assessment_or_result_completion_unverified`로 보호한다.

물리 회수는 기존 v1/v2 저장소의 만료 commit·manifest·공유 blob·index 절차를 따른다. 다른 결과가 공유하는 내용과 진행 reader는 보호한다. 단계별 중단 후에는 같은 삭제 계획으로 복구하며, 이미 확정된 계획의 복구에 새 달력을 요구하지 않는다. 최초 자료 집합에서 승인된 삭제분을 제외한 집합 hash를 계속 대조하므로, 우연히 사라진 원본을 정상 만료로 바꾸지 않는다.

과거 복기의 완료 확인에 쓰이는 `model_publications`와 `publication_commits`는 보존한다. 이 둘도 생산이 종료된 초기 집합이므로 새 운영마다 계속 증가하지 않는다. 개별 삭제 표시는 최초 전환 때 존재한 기록 수 안에서만 생기며, 모델·예측·시작 기록의 각 종류가 모두 종료되면 그 종류의 개별 표시를 제거하고 영역 종료 상태로 합친다. 현재 보유와 주문 원장 또는 전체 저장소의 고정 용량을 보장하는 계약은 아니다.

지원 범위 안의 과거 예측 성과는 선택된 사례 ID로만 예측·시작 기록을 읽는다. 한 번에 최대 200개 사례를 받으며, 전체 예측 본문을 다시 순회하지 않는다. 지원이 끝난 과거 요청에는 `expired`와 요청 건수를 반환하고, 평가 분모와 coverage는 확인할 수 없는 값으로 남긴다. 결과가 없는 새 자료를 성과 0이나 성공한 빈 평가로 처리하지 않는다. 원본 모델을 제거해도 기존 복기의 완료 상태와 저장 결과가 유지되는지, 지원되는 예측 수치가 같은지 격리 시험으로 확인했다.

이번 구현·검증에서는 운영 데이터에 이행·삭제를 실행하지 않았다. 일반 판단·전달·평가·검증 입력 전체의 원본 회수는 별도의 소비자 전환이 필요하다.


## 정기 채점 대상의 별도 목록

`scoring_targets`는 MA20 정기 채점이 전체 과거 판단·접수·전제를 다시 열어 대상을 찾던 경로를 전환한다. 최초 전환은 명시적으로 실행한다.

```sh
.venv/bin/python agent/run.py migrate-scoring-targets --dry
.venv/bin/python agent/run.py migrate-scoring-targets
```

사전 확인은 읽기 전용이다. 실제 전환은 기존 접수 증명과 전제 본문·대상·판단 연결을 대조하고, 원본 읽기·접수가 진행 중이면 미룬다. 최초 자료의 상한은 대상 20,000개·목록 내용 32MiB이며, 손상·누락·전환 중 추가 접수는 전환을 중단한다. 이 명령으로 판단·접수·전제 원본을 삭제하지 않는다. 이번 구현 시험은 임시 사본에서만 전환했다.

전환 후 새 접수는 목록 반영 의도를 먼저 저장한다. 접수 완료 파일 발행과 목록 확정 사이에서 멈추면 해당 미완료 ID만 대조해 복구한다. 이미 검증해 저장한 판단의 접수가 중단된 경우에는 같은 본문·전제 ID·접수 ID를 사용해 재시도한다. 새 접수로 위장하거나 기존 완료 기록을 지우지 않는다. 미확정 접수 의도는 최대 200개이고, 접수 여부가 불확실한 내용을 자동으로 성공 또는 취소 처리하지 않는다.

`knowledge_as_of`를 따로 지정하지 않은 정기 채점에서만 새 목록을 사용한다. 진행 중·정정 대기·정정 필요 상태와 종료일 기준 최근 20거래일의 완료 대상을 조회한다. `finalized_unknown`은 unknown 상태로 유지한다. 명시적인 과거 시점 재실험은 기존 reader를 사용하며, 이 전환을 일반 판단·평가 원본 삭제의 근거로 사용하지 않는다. 거래소 달력이 없으면 종료 날짜를 추측해 목록을 줄이지 않고 보존 중인 대상을 조회한다.

한 번에 200개·2MiB까지 반환하고, 초과하면 확인한 전체 분모와 미완료 상태를 유지한다. 다음 정기 실행은 ID 순서의 다음 대상부터 이어가며, 마지막에 도달하면 처음으로 돌아간다. 이 위치는 완료 증명이 아니므로 중단된 대상도 다음 순회에서 다시 처리한다. 단일 항목의 용량 초과나 목록 손상은 정상적인 빈 결과로 바꾸지 않는다. 분모를 확인할 수 없으면 `expected_count`도 미확인이다.

평가·정정 상태와 목록은 같은 저장 작업에서 갱신한다. 정정 대기 표시가 필요한 대상이 200개를 넘는 경우에도 끝까지 표시한다. 진행 중 대상·진행 검증의 기간·필수 참조는 보관하고, 종료된 목록은 기존 개선 저장소 GC에서 행·revision·개별 연결을 정리한다. 목록과 접수 의도에는 현재 revision만 남긴다. 삭제된 과거 전제를 새로운 접수에 재사용하는 요청은 목록을 재생성하지 않고 거절한다. 종료 증명이 없는 원본은 삭제 대상으로 간주하지 않는다.

목록의 삭제 이후 직접적인 과거 목록 조회는 지원 종료를 표시한다. 실제 과거 재실험은 여전히 원본이 필요하며, 실행 맥락·시세 관측·기존 결과를 읽는 나머지 채점 경로까지 전환된 것은 아니다. 정기 채점 전체의 실행 비용이나 운영 저장량이 일정해졌다고 주장하지 않는다.
